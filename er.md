## 1. Границы предметной области

ER-диаграмма описывает структуру базы данных для «Портала медицинского освидетельствования и страхования» (раздел 3 дорожной карты). Модель охватывает регистрацию пользователей и разграничение их ролей через привязку к организациям, подачу и обработку заявок на медосвидетельствование и оформление полиса ОМС/ДМС, ведение полной истории переходов статусов, запросы на доработку, хранение прикреплённых документов и итоговых результатов оказания услуг.

## 2. Сущности и атрибуты

| Сущность | Описание |
| :--- | :--- |
| **USER (Пользователь)** | Единая таблица всех физических лиц (иностранных граждан и сотрудников организаций). Хранит уникальный номер телефона для авторизации по SMS, ФИО и гражданство (используется для проверки условий п. 3.3). |
| **ORGANIZATION (Организация)** | Справочник медицинских организаций (п. 3.1, 3.2) и страховых компаний по месту пребывания (п. 3.3). Поле `service_area` позволяет проверять совпадение с `place_of_stay` заявителя без строгой привязки к фактическому адресу офиса. |
| **EMPLOYEE (Сотрудник)** | Промежуточная сущность между `USER` и `ORGANIZATION`. Определяет роль сотрудника (врач, оператор, страховой агент) и его привязку к конкретной организации. |
| **APPLICATION (Заявка)** | Центральная сущность процесса. Связывает заявителя и организацию, хранит тип услуги (`app_type`), текущий статус и анкетные данные для проверки применимости пунктов 3.1–3.3 и контроля сроков (`place_of_stay`, `entry_date`, `entry_purpose`, `stay_duration_days`, `patent_application_date`, `has_existing_policy`, `planned_work_start_date`). |
| **STATUS_HISTORY (История статусов)** | Журнал всех изменений статуса заявки. Поле `initiator_type` указывает, кто инициировал переход (`applicant` — заявитель, `employee` — сотрудник, `system` — автоматическое событие системы), а опциональный внешний ключ `changed_by_user_id` ссылается на конкретного пользователя (либо равен `NULL` для системных переходов). |
| **MEDICAL_RESULT (Результат медосвидетельствования)** | Итоговое заключение медорганизации. Фиксирует результаты проверок на отсутствие наркомании, инфекционных заболеваний, представляющих опасность для окружающих, и ВИЧ-инфекции, а также дату выдачи и итоговый статус. |
| **INSURANCE_POLICY (Страховой полис)** | Выпущенный полис ОМС или ДМС с уникальным номером, датой оформления (`issue_date`) и сроком действия. |
| **REQUEST_FOR_DOCS (Запрос доработки)** | Запрос сотрудника на предоставление дополнительных документов или исправление данных в заявке с указанием причины и флага выполнения. |
| **DOCUMENT (Документ)** | Файлы, прикреплённые к заявке при первичной подаче (`request_id = NULL`) или догруженные в ответ на конкретный запрос доработки (`request_id` ссылается на `REQUEST_FOR_DOCS`). **Ограничение целостности:** значение `request_id` должно ссылаться на запись `REQUEST_FOR_DOCS`, у которой `app_id` совпадает с `app_id` текущего документа. Это гарантирует, что файл не может быть прикреплён к запросу по другой заявке. Ограничение реализуется на уровне БД через CHECK-подзапрос или триггер (в PostgreSQL — `ASSERT` в триггере `BEFORE INSERT/UPDATE`). |

## 3. Семантика связей (Кардинальность)

## 3. Семантика связей (Кардинальность)

- `USER ||--o{ EMPLOYEE` — **Один-ко-многим**. Один пользователь может иметь несколько записей о трудоустройстве (в разных организациях или должностях).
- `ORGANIZATION ||--o{ EMPLOYEE` — **Один-ко-многим**. Одна организация имеет множество сотрудников.
- `USER ||--o{ APPLICATION` — **Один-ко-многим**. Один иностранный гражданин может подать несколько заявок (например, на медосвидетельствование и на полис).
- `ORGANIZATION ||--o{ APPLICATION` — **Один-ко-многим**. Одна организация обрабатывает множество заявок.
- `APPLICATION ||--o{ STATUS_HISTORY` — **Один-ко-многим**. У каждой заявки хранится полная последовательность переходов статусов.
- `USER |o--o{ STATUS_HISTORY` — **Ноль-или-один ко многим**. Переход статуса может быть инициирован конкретным пользователем (как заявителем при подаче или повторной отправке, так и сотрудником при проверке) либо выполнен системой автоматически (`changed_by_user_id = NULL`).
- `APPLICATION ||--o| MEDICAL_RESULT` — **Один к нулю-или-одному**. Заявка завершается заключением только при `app_type = 'medical'`. Для заявок на полис этот результат всегда отсутствует (взаимоисключающее ограничение на уровне бизнес-логики).
- `EMPLOYEE ||--o{ MEDICAL_RESULT` — **Один-ко-многим с ограничением организации**. Сотрудник может оформить заключение только по заявке, направленной в его организацию: при создании записи проверяется равенство `EMPLOYEE.org_id = APPLICATION.org_id` (через `app_id` в `MEDICAL_RESULT`).
- `APPLICATION ||--o| INSURANCE_POLICY` — **Один к нулю-или-одному**. Заявка завершается полисом только при `app_type = 'insurance'`. Для медицинских заявок полис всегда отсутствует.
- `EMPLOYEE ||--o{ INSURANCE_POLICY` — **Один-ко-многим с ограничением организации**. Сотрудник страховой компании может выдать полис только по заявке, направленной в его организацию: при создании записи проверяется равенство `EMPLOYEE.org_id = APPLICATION.org_id` (через `app_id` в `INSURANCE_POLICY`).
- `APPLICATION ||--o{ REQUEST_FOR_DOCS` — **Один-ко-многим**. По одной заявке может быть сформировано несколько запросов на исправление.
- `EMPLOYEE ||--o{ REQUEST_FOR_DOCS` — **Один-ко-многим с ограничением организации**. Сотрудник может направить запрос на доработку только по заявке, направленной в его организацию: при создании записи проверяется равенство `EMPLOYEE.org_id = APPLICATION.org_id` (через `app_id` в `REQUEST_FOR_DOCS`).
- `APPLICATION ||--o{ DOCUMENT` — **Один-ко-многим (нуль-или-много)**. К одной заявке прикрепляется один или несколько файлов. Нулевое количество допустимо исключительно на этапе создания черновика заявки до момента прикрепления файлов пользователем.
- `USER ||--o{ DOCUMENT` — **Один-ко-многим**. Пользователь загружает множество документов (связь по полю `uploaded_by`).
- `REQUEST_FOR_DOCS |o--o{ DOCUMENT` — **Ноль-или-один ко многим**. Документ может быть прикреплён в рамках одного конкретного запроса на доработку (или не относиться к запросу при первичной подаче заявки), при этом к одному запросу доработки может относиться несколько загруженных документов. **Ограничение целостности:** при заполненном `request_id` значение `app_id` в `DOCUMENT` должно совпадать со значением `app_id` в связанной записи `REQUEST_FOR_DOCS` (см. описание сущности `DOCUMENT` в § 2).

## 4. Соответствие сценариям из `use_case.md`

1. **Авторизация и роли (`UC1`, `UC2`, `UC8`):** все участники регистрируются и входят по номеру телефона (`USER.phone`). Принадлежность к роли сотрудника медорганизации или страховой определяется через `EMPLOYEE` и `ORGANIZATION.org_type`.
2. **Медосвидетельствование (`UC3`, `UC9`, `UC4`, `UC7`):** гражданин выбирает медорганизацию и создаёт `APPLICATION` (`app_type = 'medical'`), что фиксируется в `STATUS_HISTORY` с `initiator_type = 'applicant'`. Сотрудник медорганизации загружает `MEDICAL_RESULT` и обновляет статус (`initiator_type = 'employee'`).
3. **Страхование (`UC5`, `UC11`, `UC10`, `UC14`):** гражданин выбирает страховую компанию и создаёт `APPLICATION` (`app_type = 'insurance'`). Сотрудник страховой оформляет `INSURANCE_POLICY`.
4. **Доработка и история статусов (`UC6`, `UC12`, `UC13`):** при выявлении ошибок сотрудник создаёт `REQUEST_FOR_DOCS` и переводит заявку на доработку. По запросу сотрудника гражданин может исправить данные самой заявки (анкеты) и/или загрузить недостающие файлы (`DOCUMENT` с заполненным `request_id`). Повторная отправка фиксируется в `STATUS_HISTORY` с указанием `changed_by_user_id` заявителя и `initiator_type = 'applicant'`.

## 5. Поддержка правил и сроков из дорожной карты (Раздел 3)

Применимость услуг и контроль сроков определяются строго по условиям пунктов 3.1–3.3 без дополнительных исключений:

- **Пункт 3.1 — Медицинское освидетельствование (трудовая деятельность):**
  - *Условие включения:* иностранный гражданин прибыл в РФ в целях осуществления трудовой деятельности (`APPLICATION.entry_purpose = 'трудовая'`).
  - *Срок:* в течение **30 календарных дней со дня въезда** (`APPLICATION.entry_date`), **либо при обращении с заявлением об оформлении патента или разрешения на работу** (срок контролируется по дате `APPLICATION.patent_application_date`).
  - *Результат:* заключение в `MEDICAL_RESULT` об отсутствии наркомании, опасных инфекционных заболеваний и ВИЧ.
- **Пункт 3.2 — Медицинское освидетельствование (длительное пребывание без трудовой деятельности):**
  - *Условие включения:* иностранный гражданин прибыл на длительный период **более 90 суток** (`APPLICATION.stay_duration_days > 90`) в целях, **иных от осуществления трудовой деятельности** (`APPLICATION.entry_purpose = 'иная'`).
  - *Срок:* в течение **90 календарных дней со дня въезда** (`APPLICATION.entry_date`).
  - *Результат:* аналогичное заключение в `MEDICAL_RESULT`.
- **Пункт 3.3 — Полис ОМС или ДМС:**
  - *Условие включения:* гражданство заявителя (`USER.citizenship`) — Азербайджан, Таджикистан, Узбекистан, Молдова, Украина, Киргизия, Казахстан или Армения **при отсутствии действующего полиса** (`APPLICATION.has_existing_policy = false`), если полис необходим для трудоустройства.
  - *Срок и место:* **до начала трудовой деятельности** (контролируется путем сравнения `INSURANCE_POLICY.issue_date` и `APPLICATION.planned_work_start_date`), при этом проверяется совпадение `APPLICATION.place_of_stay` с территорией обслуживания выбранной страховой компании (`ORGANIZATION.service_area`).
  - *Результат:* оформленный полис ОМС или ДМС в `INSURANCE_POLICY`, выданный страховой компанией по месту пребывания.
