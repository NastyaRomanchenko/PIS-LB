## 1. Границы предметной области

ER-диаграмма отражает структуру базы данных для портала, автоматизирующего процессы медицинского освидетельствования и страхования. Модель охватывает учет пользователей, разграничение их ролей через сущность трудоустройства, процесс подачи и обработки заявок, хранение полной истории изменения статусов, а также результаты освидетельствования, полисы и прикрепленные документы.

## 2. Сущности и атрибуты

| Сущность | Описание |
| :--- | :--- |
| **USER (Пользователь)** | Единая таблица для всех физических лиц. Содержит базовые данные (телефон, ФИО). |
| **ORGANIZATION (Организация)** | Справочник медицинских учреждений и страховых компаний. |
| **EMPLOYEE (Сотрудник)** | Промежуточная сущность, реализующая связь «Многие-ко-многим» между `USER` и `ORGANIZATION`. Позволяет одному человеку работать в нескольких местах, а одной организации иметь много сотрудников. |
| **APPLICATION (Заявка)** | Центральная сущность. Связывает гражданина и организацию, фиксирует тип услуги и текущий статус. |
| **STATUS_HISTORY (История статусов)** | Сущность для аудита. Хранит лог всех изменений статуса заявки с датами, сотрудником (кто изменил) и комментариями. |
| **DOCUMENT (Документ)** | Файлы, прикрепленные к заявке. Содержит ссылку на пользователя, который их загрузил. |
| **MEDICAL_RESULT (Результат медосвидетельствования)** | Создается сотрудником медорганизации по завершении проверки. |
| **INSURANCE_POLICY (Страховой полис)** | Создается сотрудником страховой компании. |
| **REQUEST_FOR_DOCS (Запрос документов)** | Фиксирует факт того, что сотрудник нашел ошибки и вернул заявку на доработку. |

## 3. Семантика связей (Кардинальность)

*   `USER ||--o{ EMPLOYEE` — **Один-ко-многим**. Один пользователь может иметь несколько записей о трудоустройстве (в разных организациях).
*   `ORGANIZATION ||--o{ EMPLOYEE` — **Один-ко-многим**. Одна организация нанимает множество сотрудников.
*   `USER ||--o{ APPLICATION` — **Один-ко-многим**. Один гражданин может подать множество заявок.
*   `ORGANIZATION ||--o{ APPLICATION` — **Один-ко-многим**. Одна организация обрабатывает множество заявок.
*   `APPLICATION ||--o{ STATUS_HISTORY` — **Один-ко-многим**. У одной заявки может быть множество записей об изменении статуса.
*   `EMPLOYEE ||--o{ STATUS_HISTORY` — **Один-ко-многим**. Конкретный сотрудник может изменить множество статусов.
*   `APPLICATION ||--o| MEDICAL_RESULT` — **Один-к-одному (или ноль)**. У заявки на медосвидетельствование может быть только один итоговый результат.
*   `EMPLOYEE ||--o{ MEDICAL_RESULT` — **Один-ко-многим**. Сотрудник может оформить множество заключений.
*   `APPLICATION ||--o| INSURANCE_POLICY` — **Один-к-одному (или ноль)**. У заявки на полис может быть только один выпущенный полис.
*   `EMPLOYEE ||--o{ INSURANCE_POLICY` — **Один-ко-многим**. Сотрудник страховой может выдать множество полисов.
*   `APPLICATION ||--o{ DOCUMENT` — **Один-ко-многим**. К одной заявке можно прикрепить несколько файлов.
*   `USER ||--o{ DOCUMENT` — **Один-ко-многим**. Пользователь может загрузить множество документов (связь по полю `uploaded_by`).
*   `APPLICATION ||--o{ REQUEST_FOR_DOCS` — **Один-ко-многим**. По одной заявке сотрудник может сделать несколько запросов на исправление.
*   `EMPLOYEE ||--o{ REQUEST_FOR_DOCS` — **Один-ко-многим**. Сотрудник может направить множество запросов на доработку.

## 4. Соответствие бизнес-логике

Данная структура полностью поддерживает сценарии, описанные в диаграмме прецедентов:

1.  **Медосвидетельствование (п. 3.1, 3.2):** Гражданин (`USER`) создает `APPLICATION` (тип `medical`), прикрепляет `DOCUMENT`. Сотрудник медорганизации (`EMPLOYEE`) обрабатывает её и создает `MEDICAL_RESULT`.
2.  **Страхование (п. 3.3):** Гражданин создает `APPLICATION` (тип `insurance`). Сотрудник страховой (`EMPLOYEE`) создает `INSURANCE_POLICY`.
3.  **Доработка и аудит:** Если сотрудник находит ошибки, создается `REQUEST_FOR_DOCS`. При любом изменении статуса в `APPLICATION` обновляется поле `current_status`, а в таблицу `STATUS_HISTORY` добавляется запись с датой, ID сотрудника (`employee_id`) и комментарием. Гражданин может загрузить новые `DOCUMENT` для исправления.
